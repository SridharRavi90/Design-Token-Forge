The Question That Changed Everything
What if design decisions were code from the very beginning — not Figma values that engineers have to translate?

That question is what Design Token Forge was built to answer.

Not a handoff tool.
A shared language.

Every design tool I'd seen treated the "gap" as an export problem. Generate some JSON. Paste it into the codebase. Done? No. That's just automating the translation. The same decision is still being made twice — just faster.

The insight was simpler than that: what if there was no translation step at all? What if the decision — "our primary blue is #4F6EF7" — existed once, in a canonical form that Figma, the web app, the mobile app, and the email template all read from directly?

That's a design token. And a token system done right isn't a spreadsheet of hex values — it's a living vocabulary that an entire organization speaks.

🔡

The token system has layers. At the bottom are the raw color values — a 22-step palette for every role (brand, danger, success, neutral...). Above that, semantic tokens give them meaning: "this is what we use for error states." At the top, component tokens make it concrete: "this is the background of a danger button."

Change the raw palette. Everything above it adapts. That's not automation — that's architecture.

/* T0 — Primitives: the raw palette */ :root { --prim-brand-500: #4F6EF7; /* Change this once → */ --prim-brand-600: #2C47C7; } /* T1 — Semantic: what it means */ :root { --color-action-bg: var(--prim-brand-500); /* → flows here */ --color-action-bg-hover: var(--prim-brand-600); } /* T2 — Component: how it's applied */ .button-primary { background: var(--color-action-bg); /* → and here */ color: var(--color-action-text); } /* → Every button on every platform, updated. */

💡 A fair question — how does the frontend developer actually get notified?

This is the right thing to wonder. Here's the honest answer: most of the time, they don't need to be. When a developer writes background: var(--brand-500), they're referencing a name — not a hex value. When that name's value changes, their code updates automatically on the next build. No one needed to tell them anything.

📦 Value changes (most common)

A color updates, a spacing value shifts. The developer's code already uses the token name. The updated tokens file is published as a new package version. Their next build picks it up automatically. Zero action required.

🔖 Structural changes (rare)

A token is renamed or a new one is added. This triggers a versioned release (semver major bump) with a CHANGELOG entry — the same workflow as any package dependency update. CI lint checks catch anything missed. Developers review, update, and move on.
